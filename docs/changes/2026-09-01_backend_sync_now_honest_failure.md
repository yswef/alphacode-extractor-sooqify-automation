# `/api/sync/now` يرجّع فشل المزامنة الحقيقي بدل "نجاح" ظاهري

**التاريخ:** 2026-09-01
**الملفات المعدَّلة:** `backend/app/services/sync_service.py`، `backend/app/api/routes/sync_routes.py`

## التعديل

`sync_pull_updates()` (بـ`sync_service.py`) كانت تبتلع خطأ `sync_call("pull", ...)` بصمت:
تخزّنه بـ`state["last_error"]` فقط، بدون رفعه أو إعادته لأي طرف يستدعيها. صارت ترجع
نص الخطأ (`return error`) عند الفشل، وتبقى ترجع `None` (ضمنياً) عند النجاح أو لما
المزامنة معطّلة.

`trigger_sync_now()` (بـ`sync_routes.py`، مسار `/api/sync/now`) كانت تتجاهل تماماً نتيجة
`sync_pull_updates()`، وترجع `{"success": True, ...}` طالما ما صار Python exception —
حتى لو فشل الـpull فعلياً بخطأ شبكة. صارت تفحص القيمة المُرجَعة: لو فيها خطأ، ترجع
`{"success": False, "error": <النص>, "status": ..., "pending_queue": ...}` بكود 502 —
نفس النمط المستخدم فعلاً بـ`/api/brands`.

## السبب

اختبار حقيقي (curl مباشر) كشف: `/api/sync/now` يرجع `HTTP 200` و`"success": true` حتى
وقت فشل `sync_call` بخطأ شبكة فعلي (`WinError 10013` — راجع تشخيص جلسة سابقة)، بينما
النص الحقيقي للخطأ كان مدفوناً جوا `status.last_error` فقط. بـ`popup.js`، دالة
`triggerSyncNow()` تفحص `data.success` فعلاً وتعرض الخطأ عبر `showStatus()` لو
`false` — لكن بما إن الباك اند كان يرجع `true` دايماً، المستخدم يشوف "تمت المزامنة."
حتى لما المزامنة فشلت فعلياً. النتيجة: لا حاجة لأي تعديل بـ`popup.js` — المشكلة كانت
حصراً بالباك اند اللي يخفي حقيقة الفشل.

## كيف يعمل المنطق الجديد

`sync_pull_updates()` تصير تُرجع نص الخطأ الحرفي القادم من `sync_call` مباشرة عند
الفشل. `trigger_sync_now()` تستقبل هذي القيمة وتقرر شكل الاستجابة بناءً عليها، بدل
افتراض النجاح لمجرد عدم وجود exception. باقي مستدعيات `sync_pull_updates()` (بـ
`app.py` الميت، `/api/sync/pull`، `ai_helpers.py`) لا تتأثر — كلها تستدعيها كجملة
مستقلة بدون استخدام القيمة المُرجَعة، فإضافة `return` لا تكسر أي شيء عندهم.

## التحقق الفعلي

- `python -c "import py_compile; ..."` نجح لكلا الملفين بدون أخطاء.
- تشغيل الباك اند فعلياً + `curl -X POST http://127.0.0.1:5000/api/sync/now` أثناء
  اتصال شبكة سليم فعلاً: رجع `{"success": true, "status": {"last_error": "", ...}}` —
  المسار السليم يعمل كما هو متوقع بدون كسر أي شيء.
- لم يتيسّر تكرار حالة فشل الشبكة (`WinError 10013`) فعلياً بهالجلسة لاختبار مسار
  `success: false` مباشرة (الشبكة كانت سليمة وقت الاختبار) — التحقق هنا مبني على قراءة
  المسار الشرطي فعلياً بالكود بعد التعديل + نجاح المسار السليم، مو تشغيل فعلي لحالة
  الفشل تحديداً.
